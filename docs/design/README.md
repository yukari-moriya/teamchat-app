# 設計書一式（目次）

チームチャットアプリの決めごとの正本です。仕様書（`docs/spec.md`）とモックアップ（`mockup/`）を読んで設計に落とし、7つの実装単位（`acceptance.md` の1〜7）を作り終えた時点の実物と一致させてあります。

実物と設計書が食い違ったら、**コードより先にここを直します**。

---

| ファイル | 中身 | 主な章 |
|:--|:--|:--|

## 2. 番号の読み方

設計書どうしは、番号で指し合っています。

| 番号 | 何か | どこで決めているか |
|:--|:--|:--|
| F-xx | 機能 | `features.md` の1章 |
| Q-xx | クライアントへの確認事項 | `questions.md` の1〜7章・9章 |
| R-xx | クライアントの回答 | `questions.md` の10章（原文）。Qとの対応は11章 |
| D-xx | 設計側の決定（クライアントには聞かないもの） | `questions.md` の8章。理由も書いてある（選ばなかった案を書いたものもある） |
| SC-xx | 画面 | `screens.md` の1章 |
| AC-n-m | 受け入れ条件（n は実装単位） | `acceptance.md` の1章 |
| TP-n-xx | テスト観点（n は実装単位） | `acceptance.md` の2章 |
| ［設計］ | 仕様書・モックアップに根拠が無く、設計で決めたもの | 各ファイルの中の印 |

回答が返ってこず設計側で決めた確認事項は、`questions.md` の13章に Q の番号で載っています（D-xx ではありません）。

## 4. 直すときの決まり

- 仕様書（`docs/spec.md`）は変えない。仕様書への疑問は、`questions.md` の確認事項に足す
- 決めを変える・足すときは、`questions.md` の8章に D-xx を続きの番号で足し（いまは D-43 まで）、反映先のファイルも同じ変更の中で直す
- 1ファイルに違う種類を混ぜない。上の表の分け方を守る
- 図は Markdown の中に Mermaid で書く（画像ファイルを置かない）。クラス図は作らない（Laravel の MVC に乗る。`behavior.md` の冒頭）
- まだ決まっていないことは、`screens.md`・`data.md`・`permissions-api.md`・`behavior.md` の末尾の「まだ決まっていないこと」に置く（いまはどれも無い）

## 5. 書く量の方針

設計書は「多く書いたほうが良い」ものではなく、あとから読む人が判断に使える分だけを書きます。

| どこ | どこまで書くか |
|:--|:--|
| 画面項目定義 | 主要な画面だけ。同じ形の画面は「◯◯との差分」で済ませる |
| シーケンス図 | 代表を1本だけ |
| 受け入れ条件 | 1つの実装単位につき2〜4行（人が1行ずつ確かめる約束なので、増やしすぎない） |
| テスト観点 | 観点だけ。組み合わせの網羅はテストコードの仕事 |
| クラス図 | 作らない |
