# HTTP層の書き方

コントローラ・フォームリクエスト・ポリシー・ルートと、入力チェックの決まり。**理由まで書いてあるのは、理由を知らないと直したくなる形をしているから。**正本は `docs/design/permissions-api.md`、入力チェックと文言は `docs/design/screens.md` の4章、例外の扱いは `docs/design/behavior.md` の3章。公開API（`routes/api.php` を含む）は `permissions-api.md` の3章を先に読む。

## 404 の判定を、403 より先に済ませる

1. **URL の子がそのチャンネルのものか** → 違えば **404**（ルートの `scopeBindings()`）
2. **そのチャンネルが見えるか** → 見えなければ **404**（`can:view,channel` のグループ。`ChannelPolicy` の `view` が `denyAsNotFound()` を返す）
3. **作成者か・投稿者本人か・まだ削除されていないか** → 違えば **403**（ルートの `can` とポリシー）

1 が 2 より先に動くのは、ルートのモデルの解決が `can` より先だから。どちらも同じ 404 なので、区別はつかない。崩してはいけないのは、**404 がすべて済んでから 403 を返す**こと。先に 403 が返ると、見えないプライベートチャンネルがあることが漏れる。1 を落とすと、見えるチャンネルのURLの下に別チャンネルのメッセージIDを差し込むだけで手が届く。

判定はルートに書き、コントローラで `authorize()` や `abort_unless()` を使った権限の確認を足さない。`{channel}` のルートはこのグループに置き、ID の引数には `whereNumber` を付ける。

次の3つは、形が違うのに理由がある。

- **公開チャンネルのメンバー管理**は、作成者かを見る前に公開かを見て 404（D-23）。
- **メンバーを外す `{user}`** は `scopeBindings()` で絞らない。権限より先に動くので、404 と 403 の違いで誰がメンバーかが分かる（D-35）。
- **返信への返信**は、返信用の FormRequest が入力チェックより先に 404 にする。権限ではないので、ポリシーに置かない（D-38）。

## フォームリクエストに `authorize()` を書かない

権限はルートの `can` が確かめる。ここにも置くと同じ判定が2か所になり、拒否は 403 になるので、404 にすべき場面で崩れる。`authorize()` が無ければ、Laravel は許可として扱う。フォームリクエストは入力チェックを受け持つ（D-38 の 404 だけが例外）。

## 入力チェックはフォームリクエストに置く

ルートの `can` はフォームリクエストより先に動くので、見えないチャンネルへの送信は、入力チェックの前に 404 になる。エラー文から、チャンネルの存在が漏れることはない。コントローラで `validate()` は呼ばない（Fortify の新規登録は `CreateNewUser`）。

- 各欄のルールは `bail` で始める。1つの欄に出すエラーは1つ。
- `min`・`max` を使う欄は、`string` を付けるか、文字列だと確かめた値を渡す。**配列だと、要素の数を数える。**
- 型を変える前に、文字列かを確かめる。配列を `(string)` に変えると 500 になる。
- 複数行の欄は、改行の CRLF をそろえてから文字数を数える。そろえないと、改行が2文字になる。
- エラーで戻る先が送った画面と違うときだけ、`getRedirectUrl()` を書き換える。
- 文言は `screens.md` の4章のとおりにする。`app/Rules`・`app/Actions`・`lang` に書く文言も同じ。

## URL・HTTPメソッド・遷移先を自分で決めない

URL・ルート名・クエリ・フォームの項目名の一覧は、`permissions-api.md` の2章にある。更新は `PUT`、削除は `DELETE` で、HTMLのフォームからは `POST` + `@method('PUT')`・`@method('DELETE')` で送る。

新しく書くリダイレクトは、名前のあるルートは名前で指す。チャンネルの画面の行へ戻る URL は `Message::url()` で作る。

## 受け取った値をそのまま信じない

- `thread`・`edit` の ID は、`Channel` の `threadOrigin()`・`findMessage()` で探す。数字かを確かめないと、MySQL が「1abc」を 1 と読む。
- 保存には、入力チェックを通った値だけを渡す。投稿者・チャンネル・作成者・返信の元は、サーバー側で関連を使って決める。
- 複数の表への書き込みは `behavior.md` 3-2 に従う。

## チャンネルの作成者に特権を持たせない

**チャンネルを作った人であっても、他人が書いたメッセージは編集・削除できない。**「作成者かどうか」と「投稿者本人かどうか」は別の判定で、ポリシーの中で混ぜない（`permissions-api.md` 1-3 の b）。

## UIで隠したことを、判定の代わりにしない

ボタンを出していない・`disabled` にしている、はサーバ側の判定の理由にならない。作成者チェック・投稿者本人チェック・削除確認の入力の一致・作成者を外せない制御は、**すべてサーバ側で確かめる**。

## 見えないものへの応答は404で揃える

存在しないID・自分がメンバーでないプライベートチャンネル・チャンネルとメッセージの組み合わせ違い・返信を元に指すURLは、**すべて同じ404**。区別できる応答を返すと、その差から存在が分かってしまう。

見えるチャンネルでの「権限が無い操作」は 403（`permissions-api.md` 1-5）。
