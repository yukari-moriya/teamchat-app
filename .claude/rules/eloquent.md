# モデルとデータベースの書き方

正本は `docs/design/data.md`。ここは**Laravel の既定に素直に従うと壊れるところ**を中心に挙げる。

## `SoftDeletes` トレイトを使わない

`messages` の `deleted_at` は Laravel の論理削除とは**意味が違う**（D-05。経路ごとの扱いは `questions.md` の「D-05 の補足」）。

- 削除しても **`body` はクリアしない**。削除済みメッセージは「このメッセージは削除されました」の枠として画面に残り、投稿者名・日時・返信件数も残る。返信も続けられる
- そのためチャンネル表示（F-14）とスレッド表示（F-18）は **`deleted_at` を問わず全件取得**する。`SoftDeletes` のグローバルスコープはこれを既定で弾くので、トレイトを付けると画面から枠ごと消える
- トレイトが無いので **`$message->delete()` は行が消える**。メッセージの削除は `markAsDeleted()` だけを通す

逆に**検索（F-21）と公開API（F-24）は削除済みを除く**。条件を自分で書かず、`Message` の `notDeleted()` を通す。ここを落とすと削除済みの本文が外に漏れる。

**チャンネルの削除は行を消す**。`channel_user` と `messages` は、外部キーの CASCADE で一緒に消える。メッセージの削除とは別物。

## 「編集済み」を `updated_at` で判定しない

真偽の列 `is_edited` で判定する（D-09）。`updated_at` は削除（`deleted_at` の更新）でも動くので、編集以外でも印が付いてしまう。本文を直すときは `Message` の `edit()` を通す。本文が変わらない保存では、印を付けない（D-25）。

## 返信を別テーブルにしない

`messages` の自己参照（`parent_id`）。NULL ならチャンネルに直接書かれたメッセージ、値が入っていれば返信（D-06）。

- **返信は1段まで**だが、これは**DBの制約ではなくアプリ側で確かめる**
- `channel_id` は返信も持ち、元のメッセージと常に同じにする。検索で見られるチャンネルを絞るためにも使うので、冗長だからと消さない

## 返信件数の列を持たない

そのつど数える。削除された返信も数える。件数の列を持つと整合性を保つ手間が要るが、この規模では見合わない。

## 日時の列と `channel_user`

- 新しい migration で `$table->timestamps()` を**使わず**、`$table->dateTime('created_at')`・`$table->dateTime('updated_at')` を手書きする。`timestamps()` は型が `timestamp` で NULL 可になり、`data.md` の定義と違う（D-20）
- `channel_user` は `(channel_id, user_id)` の複合主キーで、サロゲートIDを足さない。`created_at`（追加した日時。一覧の並びに使う）と `updated_at` を持ち、関連は `withTimestamps()` で読み書きする
- 行を作るのは**プライベートチャンネルだけ**（D-07）。作成者の行は消さない
- 複合主キーなので、同じ人の二重の追加はDBが一意制約違反で止める。「すでにメンバーです」は、先にアプリ側で確かめる

## 問い合わせの条件はモデルに寄せる

`Channel` の `topLevelMessages()`（返信でない行）・`visibleTo()`（見られるチャンネル）、`Channel` と `Message` の `inListOrder()`（並び）のように、**どの条件で絞るかをモデル側に置く**。コントローラやビューに同じ条件を書き直さない。見せてよい範囲の判断が要る場所なので、1か所に集めて名前で意図を示す。

可視範囲の絞り込みは `Channel::visibleTo()` の1本に通す。取ってきたあとに、画面で間引かない。

## `$fillable` と ID

- `$fillable` には、利用者が入力する列だけを入れる。外部キーは、サーバー側で関連を使って設定する
- 画面や URL から受け取った ID は、数字の文字列かを確かめてから探す

## 文字の比較は写しの列で

比較・検索を、DB の照合順序や `LOWER()` に任せない。そろえた写しの列で比べる（D-12。そろえ方は `data.md` の2章）。

## migration は足す

実行済みの migration は書き換えず、新しく足す。`doctrine/dbal` を入れていないので、既存の列を `->change()` で直さない。

## ファクトリは列の上限に合わせる

`users.name` は30文字（spec 5-1）。`fake()->name()` はこれを超える値を返すことがあり、当たった回だけ `Data too long` で落ちる。**列に上限があるファクトリは、faker の出力を切って渡す。**テストのデータの状態は、ファクトリの `deleted()`・`private()`・`replyTo()` を使う。

## シーダーは仕様書の内容から動かさない

初期データの中身は、`docs/spec.md` 5-4 と `features.md` の F-26 が決めている。`acceptance.md` の受け入れ条件はこのデータが入っている前提なので、テストの都合でシーダーを書き換えない。テスト固有のデータが要るならファクトリを使う。何度流しても行が増えないようにし、画面に出る日時は固定の値にする（分け方は D-30）。
