# プルリクエストを出す

PR の本文は、あとで読む人（と、`review-diff`・`uat`）が、何をどこまで確かめたかを一目で知るためのもの。
だから、書く内容は「やったこと」より「確かめたことと、確かめていないこと」を中心にする。確かめていないことを確かめたように書くと、レビューが見るべき場所を見落とす。

## 手順

### 1. 状態を確かめる

- `git branch --show-current`: `main` なら止めて、ブランチを切るよう伝える（`main` に直接コミットしない。CLAUDE.md）。ブランチ名は、イシュー1件なら `feature/issue-<番号>-<英字の短い名前>`、イシューに紐づかない直し（`.claude/` の物差し・設計書だけの修正）なら `chore/<英字の短い名前>`。
- `git status`: 未コミットの変更があれば、このブランチの作業のものかを確かめる。迷うなら聞く。`.playwright-mcp/`・`uat-shots/` など、追跡されていない作業用の物は、コミットに含めない。
- `git log origin/main..main --oneline`: `main` にだけあるコミットがあれば、PR の差分にそれも入る。そのことを伝える（`main` を先に push するかは、人が決める）。
- 差分の範囲: `git log main..HEAD --oneline` と `git diff main...HEAD --stat`。

未コミットの変更を PR に入れるときは、**ファイルを名指しで** `git add` し（`git add -A`・`git add .` は使わない）、日本語のコミットメッセージでコミットする。メッセージの終わりには、このセッションで指示された attribution の行を付ける。

### 2. 材料を集める

| 本文の節 | 集めるもの |
|:--|:--|
| 何をしたか | 差分の範囲から。実装単位（イシューの題）と、作ったものを2〜3行 |
| 関連 | 機能 ID（F-xx）。読んだ・直した設計書のファイルと章 |
| 受け入れ条件の突き合わせ | イシューの「完成の条件」にある AC-N-x を、`docs/design/acceptance.md` から**文言どおり**。判定は、実際にやったものだけ（`uat` の結果があればそれを使う）。Chrome・Edge は、実際に試した方だけ ○。試していなければ「未」。ほかの単位のあとでないと確かめられない行は、D-29（`docs/design/questions.md`）のとおり「保留」にして、メモに理由を書く |
| テスト結果 | `./vendor/bin/sail artisan test` を**実際に走らせ**、件数と失敗の内容をそのまま写す。警告があればそれも。テストにした観点（TP-N-xx）と、まだテストにしていない観点。Sail が止まっているときは `./vendor/bin/sail up -d` で起こす |
| 設計書の変更 | `git diff main...HEAD -- docs/design` と、設計書を直したコミット。直したファイルと章、**直した理由** |
| 確認してほしいこと | 迷ったところ、設計書に無くて自分で決めたこと、既存の物を残した・変えた判断。このセッションの計画や会話から拾う |

数字や文言は、実行した結果から写す。覚えている値で書かない（件数・秒数・URL がずれる）。

### 3. 本文を書く

本文は次の型で書く。本文のファイルは、リポジトリの外（作業用の領域）に置く。

- イシューに紐づく（`feature/`）: 最後に `Closes #<イシュー番号>` を入れる。
- 紐づかない（`chore/`）: 受け入れ条件は「対象外（機能の変更が無い）」、テストは、PHP のコードに触れていなければ「実行していない（理由）」と書く。`Closes` は付けない。

```markdown
## 何をしたか
実装単位 N（○○）で作ったもの。2〜3行。

## 関連
- 機能: F-xx, F-xx
- 設計書: 読んだ・直したファイルと章

## 受け入れ条件の突き合わせ
`docs/design/acceptance.md` の該当する AC-N-x を、1行ずつ。Chrome と Edge の両方で試す（0-1 の前提）。

| ID | Chrome | Edge | メモ（できなかった・食い違った点） |
|:--|:--:|:--:|:--|
| AC-N-1 | ○ | ○ | |

## テスト結果
`./vendor/bin/sail artisan test` の結果（件数と、失敗があればその内容）。
テストにした観点（TP-N-xx）と、まだテストにしていない観点。

## 設計書の変更
直した設計書のファイルと章、直した理由。なければ「なし」。

## 確認してほしいこと
迷ったところ、設計書に無くて自分で決めたこと。なければ「なし」。

Closes #<イシュー番号>
```

- 節の順と見出しは変えない。人から「〇〇も本文に入れて」と頼まれたら、**足す節**として「設計書の変更」の後ろ・「確認してほしいこと」の前に置く（型の節は消さない）。
- 確かめていないことは、確かめていないと書く。ブラウザの確認が Playwright の Chromium だけなら、そう書き、Chrome・Edge は「未」にする。テストの警告が自分の変更と関係なくても、隠さず書く。
- 本文の終わりには、このセッションで指示された attribution の行を付ける。

### 4. push して PR にする

push は頼まれたときだけ（CLAUDE.md）。「PR を出して」と頼まれたときは、その PR のための push も頼まれたものとして扱う。「本文だけ書いて」なら、push も PR 作成もしない。

1. `git push -u origin <ブランチ名>`。
2. `Permission denied (publickey)` で失敗したら、そのことを報告したうえで、`gh` の認証で HTTPS から push する（git の設定は書き換えない）。

   ```bash
   gh auth status   # ログイン済みか
   git -c credential.helper= -c 'credential.helper=!gh auth git-credential' \
     push https://github.com/<owner>/<repo>.git <ブランチ名>:<ブランチ名>
   ```

   `<owner>/<repo>` は `gh repo view --json nameWithOwner -q .nameWithOwner`。
3. `gh pr create --base main --head <ブランチ名> --title "<日本語の題>" --body-file <本文のファイル>`。

### 5. 報告する

PR の URL、本文に入れた主な点（保留・未・自分で決めたこと）、push が SSH か HTTPS だったかを伝える。
**マージはしない**。マージとブランチの削除は、頼まれたときだけ。PR を出したあとのレビューと見守りは、人が `/ship` を打てばできる。

## やらないこと

- `main` への直接コミット・直接 push。
- 確かめていない判定（AC の ○、テストの通過）を書くこと。
- `.env` を読まない・書かない。
- 追跡されていない作業用の物（`.playwright-mcp/`・`uat-shots/`）を勝手にコミットしない。
- マージ。
