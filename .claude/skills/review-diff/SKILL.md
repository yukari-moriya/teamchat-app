# PR 差分レビュー（読み専用）

PR の差分を決まった順で読み、判定つきの表で報告する。目的は、人が読む前に「どこを自分の目で見るべきか」を絞り込むこと。
そのため、コードは直さない。見つけたことは報告に書くだけにする。直すかどうかは人が決める。

## 入力

- 設計書が無い機能のときは、そのイシューに書いた受け入れ条件を突き合わせ先にする。
- PR 番号（例: `2`）。指定が無ければ聞く。
- 設計書: `docs/design/`（構成は `docs/design/README.md`）。このリポジトリの設計書は機能ごとではなく種類ごとに分かれているので、その PR の実装単位（`docs/design/acceptance.md` の 1 認証／2 チャンネル／3 メンバー管理／4 メッセージ／5 スレッド／6 検索／7 公開API）に当たる機能（F-xx）・受け入れ条件（AC-N-x）・テスト観点（TP-N-xx）を、`features.md`・`screens.md`・`data.md`・`permissions-api.md`・`behavior.md`・`acceptance.md` から拾う。PR の diff に含まれていることもある。
- 「触っていないはずの場所」: 依頼に書いてあればそれを使う。無ければ設計書の「変えないもの」の節から拾い、拾ったファイル名を報告の冒頭で示す。

## 手順

### 0. 差分を取る

`gh pr diff <番号>` を実行する。出力が大きいと保存先のファイルに切り替わるので、その場合は最後まで全部読む（途中までで判定しない）。
併せて設計書を読む。

作業ツリーは今の `main` で、PR より後のマージが載っている。PR 時点の姿を知りたいときに作業ツリーのファイルを読むと、別物を読むことになる。
diff に出ていない部分は、作業ツリーで補わず「判定できない」とし、足りない物を書く。

### 1. 設計書と突き合わせる

- diff に含まれる全ファイルを列挙し、設計書にある物（画面・ルート・テーブル・Policy・テスト観点）が揃っているか見る。
- 設計書に書いていない追加がないか見る。共通化のためのリファクタ、ヘルパーの新設、既存ファイルの書き換えが典型。
- 依存まわり（`composer.json`・`composer.lock`・`package.json`・`config/`・`.env`）が diff に出ていないかを必ず確認する。出ていなければ「差分に無し」と書く。依存の追加は設計書に無いまま入りやすく、後で気づきにくい。
- 設計書のテスト観点を番号で数え、diff のテストと対応づける。

### 2. 触っていないはずの場所を見る

指定されたファイルごとに、**消えた行（`-` の行）から先に**見る。消えた行は、既存の動きを変えた証拠になるから。追加行は設計書どおりか後で見ればよい。

- 消えた行ごとに、何に置き換わったか、動きが変わるかを書く。移動しただけなら、移動先と目で突き合わせて同じかを確かめる。
- diff に載っていないファイルは「変更なし」と判定してよい。
- 動きが変わるのに、その検証ルールやテストが diff の範囲外で見えないときは「判定できない」にする。

### 3. 中身を読む

次の観点を、この順で見る。

| 観点 | 見るところ |
|---|---|
| N+1 | 一覧や詳細で、関連データを `with()` / `load()` で先読みしているか。blade 側のアクセスが追加クエリを出さないか（`@can` が関連を引かないか）。変更していない一覧は、`with()` が diff に出るか確認する。 |
| 認可の置き場所 | 判定を Policy に置き、ルートの `can` で入力チェックより先に確かめているか（コントローラーで `authorize()` を呼ばない）。blade は `@can` で出し分けているか。`app/Policies/ChannelPolicy.php`・`MessagePolicy.php`（設計は `docs/design/permissions-api.md` の1-6）の書き方と揃っているか。認可が無いアクションは、設計書がそれを許しているか。 |
| マスアサインメント | `$fillable` の中身と、`create()` / `update()` に何を渡しているか。`$request->all()` を渡していないか。`user_id` などをサーバー側で決めているか。 |
| XSS | blade の出力が `{{ }}` か。`{!! !!}` が無いか。`style` や `href` に入る値の出どころは定数か。 |
| CSRF | すべての `<form>` に `@csrf` があるか。PUT/DELETE に `@method` があるか。 |
| 入力チェック | 入力チェックが FormRequest にあるか（コントローラーで `validate()` を呼ばない。Fortify の新規登録は `CreateNewUser`）。ルールと日本語メッセージが設計書（`docs/design/screens.md` の4章「入力チェックとエラーメッセージ」）と一字一句同じか。文字数の上限は、その表の値（メッセージ・返信は新規も編集も1,000文字、チャンネル名50文字、説明200文字など）で、新規と編集で同じ値と文言か。 |
| 書き方の揃い | CLAUDE.md の決めごとに沿っているか。実行済みマイグレーションを書き換えず、新規を1つ足しているか。テストは `tests/Feature/` で `RefreshDatabase` を使っているか。 |

| 重複 | 同じ判断や同じ問い合わせが2か所以上に写っていないか（権限の判定は Policy に1か所、共通の見た目は1か所）。設計書が「1か所にまとめる」と決めたもの（`view` の判定・見られるチャンネルの絞り込み・削除済みを除く条件・削除済みの表示）が分かれて書かれていたら、手順4 の観点でも見る。**逆に、似ているだけのものを無理にまとめていないか**も見る（例: 検索は「見られるチャンネル」、公開APIは「公開チャンネル」で、絞り込みの条件が違う。共通なのは削除済みを除く条件のほう）。 |
| 読みやすさ | ネストが深くないか（当てはまらない場合を先に返す形になっているか）。1つのメソッドが長すぎないか。コレクションのメソッドで書ける繰り返しが、手書きのループになっていないか。 |

「他の物と同じか」を比べる観点は、比べる相手（例: `ChannelPolicy` の本文、編集側のメッセージ）が diff に出ていなければ、判定できない。

## 報告

### 表の形

1行1観点で、次の4列にする。見出しは手順の1〜4ごとに分ける。

| 観点 | 判定 | 場所 | 気づいたこと |
|---|---|---|---|

- **判定**は `OK` / `要確認` / `対象外` のどれか。
- **場所**は `ファイル名:行番号`。行番号は **PR 後のファイルの行**で、diff のハンクヘッダ（`@@ -a,b +c,d @@`）の `+c` から数える。消えた行は旧の行番号を `（旧31-34）` のように添える。diff に出ない物は「diff に無し」と書く。
- **判定できないとき**は、判定を `要確認` にし、気づいたこと欄に「判定できない: 〇〇が足りない」と書く。足りない物は具体的に書く（例: 「PR 時点の `update()` 全体」「`database/migrations/` の一覧」）。推測で `OK` にしない。
- **手順4で直したほうがよいとき**は、判定を `要確認` にし、気づいたこと欄を「直したほうがよい: 」で始める。続けて、何が（場所）、設計書のどの決め（D-xx・章）と違うか、どう揃えるかを一言で書く。直し方のコードや差分は書かない。
- `OK` の行も省略しない。「見たが問題なし」と「見ていない」は違うので、読んだ証拠として残す。ただし `対象外` の行は、観点名を並べて1行にまとめてよい。

  - **モデルを持たない機能**（認証・検索など）は、`<モデル名>Controller` では判定できない。この場合は **Laravel が同じことに使う標準の名前**に揃っているかで見る（ログインは `AuthenticatedSessionController`、登録は `RegisteredUserController`、`store`／`update`／`destroy` の動詞、`routes/web.php` の名前付きルート）。何をする1本かがコントローラ名から読めれば通し、読めなければ「要確認」にする

  - **「対象外」は、その差分にその観点が出てこなかったときにだけ使う。**判定の物差しが足りないときは「対象外」にせず、**何に照らせば判定できるのかが分からない**と書いて残す（物差しのほうを直す材料になる）

### 最後に

人が自分の目で読むべき場所を**3つまで**挙げる。選ぶ基準は次の順。

1. 既存の動きに手が入った場所（判定できないものを含む）
2. セキュリティに関わる場所（認可・マスアサインメント、見せてはいけない物の出口: 見られないチャンネル・削除済みの本文・公開API）
3. diff を読むだけでは判定できない場所（見た目など。ブラウザで見るべきもの）

各項目に「何を確かめるか」を一言つける。

### 書かないこと・やらないこと

- コードを直さない。`Edit` や `Write` は使わない。
- 整形の揺れ（`sail pint` で片づく）とテストの合否（`.claude/settings.json` のフックが回す）は、機械が見るので報告に入れない。
- テストは実行しない。実行していないことは報告に書く。PR 本文は diff に含まれないので、見ていない場合はそう書く。
- 手順3の「名前」「重複」「読みやすさ」は好みが入るので、表には書くが、「最後に」の3つの枠には、設計書の呼び名の食い違い（ルート名・テーブル名・項目名）を除いて入れない。
- 件数を増やすために、軽い指摘を3つの枠に混ぜない。迷ったら 1 の「既存の動きに手が入った場所」を優先する。
