# 機能の決めごとを質問して、受け入れ条件にまとめ、Issue にする

機能の依頼は、たいてい一言で届く（例:「下書き機能が欲しい」）。
そのまま作り始めると、作り手が黙って決めたことが後から効いてくる。たとえば「下書きを `messages` に混ぜたら、チャンネルのメッセージ一覧に下書きが出た」のようなことだ。

このスキルは、作り始める前に「決めておかないといけないこと」を人に聞いて決め、結果を受け入れ条件にして、GitHub の Issue に起票する。
受け入れ条件は、あとで `uat`（画面で確かめる）や `review-diff`（PR を設計書と突き合わせる）の突き合わせ先になる。
設計書（`docs/design/acceptance.md` の AC-N-x）とも食い違わせない（食い違ったら、コードではなく `docs/design/` を先に直す。CLAUDE.md）。
そのため、曖昧に書かず、確かめられる形で書く。

コードも設計書ファイルも、この段階では書かない。決める・まとめる・Issue にする、までをやる。

## 入力

- **機能の依頼**: 依頼の文章そのまま。何を作るのか読み取れなければ、最初の質問で聞く。

## 手順

### 1. 読む

質問は、このアプリの今の作りを読んでから考える。読まずに聞くと「どの機能にもある一般論」しか出てこず、答えても実装に効かない。

- `docs/spec.md`（仕様書。変えない）と `docs/design/`（設計書一式。構成は `docs/design/README.md`）。画面に関わる機能なら `mockup/`（画面の見本）も見る。
  - 設計書は種類ごとに分かれている。機能に関わるものを読む。`questions.md` の確認事項と決定（Q-xx・R-xx・D-xx）は「決めごと」の、`acceptance.md` の AC-N-x は受け入れ条件の、書き方の手本にもなる。
  - `features.md`（機能一覧・今回作らないもの）、`screens.md` の4章（入力チェックとエラーメッセージ）、`permissions-api.md`（権限マトリクス・ルーティング）、`data.md`（テーブル定義）、`behavior.md`（例外方針）、`acceptance.md`（受け入れ条件とテスト観点）。
  - その機能の受け入れ条件が `docs/design/acceptance.md` にすでにあるときは、**そこにある文言をそのまま写す**（言い換えない。設計書とイシューで文言を揃えるため）。
- `app/`: コントローラー、モデル、Policy。
- `routes/web.php`、`database/migrations/`、`resources/views/`、`tests/Feature/`。
- `CLAUDE.md` と `.claude/rules/`。ここに書かれた決まり（設計書が正本であること、「実装前に必ず読む決定」、`with()`、日時の表示と並び、ブランチと PR の運用）は、質問せずに前提として使う。

読みながら、次のメモを取る。質問の材料になる。

- 新しい機能が **今の取得・表示・ルートにどう混ざるか**（例: チャンネルのメッセージ一覧が `messages` の返信でない行を取っている（F-18）、ルートが `{channel}` のものに絞られていない（R-01））
- 今の **入力チェック・DB の制約**（必須、文字数、NOT NULL、既存マイグレーションは書き換えない）
- **画面の初期値が入力チェックをすり抜ける場所**（例: 選択式で最初の項目が選ばれた状態で送られるので、「未入力」にならない）
- 並び（基本は古い順。検索結果は新しい順）や日時の表示など、**日時を使って決めている場所**

### 2. 決めておくことを洗い出す

**手順1で、その機能の受け入れ条件が `docs/design/acceptance.md` に見つかったときは、手順2・3（洗い出しと質問）を省き、手順4へ進む。** 決めごとは設計書（`questions.md` の Q-xx・R-xx・D-xx）で決まっているので、人に聞き直さない。見つからないとき（`acceptance.md` に無い機能）だけ、この手順2・3をやる。

次の観点で、この機能に当てはまるものを探す。全部を聞くわけではない。コードを読んで「ここは作り手が決めるしかない」と分かったものだけを残す。

| 観点 | 見るところ |
| --- | --- |
| 保存先 | 既存のテーブルに足すか、別テーブルにするか。既存テーブルに混ぜると、一覧・スレッド・検索・公開APIなど、そのテーブルを読む全部の場所に「除く」条件が要る |
| 入力チェック | 必須・文字数の上限をどこまでかけるか。DB の NOT NULL との関係。画面の初期値で素通りする項目 |
| 日時 | 並びの基準（古い順が基本）、表示の形式（日本時間の `2026/08/17 14:32`）、新規扱いにするか |
| 画面と入口 | 新しい画面を作るか。既存の画面（特にチャンネルの画面）の見た目を変えるか。`mockup/` の画面との兼ね合い |
| 権限 | 誰が見られて、誰が直せるか。他人のものを直接開いたときの応答（権限の無い操作は 403、見られないチャンネルは 404。D-15・R-01。`ChannelPolicy`・`MessagePolicy` に揃えるのが基本） |
| 件数・量 | 上限を設けるか |
| 連鎖 | 元のデータが消えたとき、関連するデータをどうするか（cascade） |
| 範囲 | 今回やらないこと（`docs/design/features.md` の2章に当たらないかも見る。例: 元に戻す操作）。入れると別の決めごとが増えるものは、先に範囲外にしてよいか聞く |

### 3. 質問する（AskUserQuestion）

（手順2のとおり、`acceptance.md` に条件が見つかったときは省く。）

- **1 回に最大 4 問**。影響が大きく、他の答えを左右するものを 1 回目に出す（保存先など）。2 回目で、1 回目の答えから出てくる細かい決めごとを聞く。
- **各質問は、それだけを読んで答えられるように書く。** 質問文に、コードで見つけた事実を 1 文入れる。
  例:「チャンネルのメッセージ一覧（`GET /channels/{channel}`）は `messages` の返信でない行を出す設計なので、下書きを `messages` に混ぜると一覧に出ます。どこに保存しますか？」
- 選択肢は 2〜4 個。**おすすめを先頭に置き、`(Recommended)` を付ける。** 説明には、選ぶと何が起きるか、何が増えるか（チェック・メッセージ・テーブル）を書く。
- **聞かないもの**: 慣習どおりで決まるもの、CLAUDE.md に書いてあるもの、コードを読めば分かること。これらは前提として置き、最後の報告に書く。聞くのは、答えで作るものが変わることだけにする。
- 質問を重ねすぎない。一般に 2 回までで決め切り、残りは「前提」にして最後に確認を取る。

### 4. まとめる

決まったら、次の 3 つを順に書く。

1. **決まったこと**: 表（項目 / 決定）。
2. **私が決めた前提**: 聞かずに置いた前提を番号つきで書く。特に、コードを読んで気づいた落とし穴（初期値で素通りする項目など）の扱いは、ここに出して、違っていたら直してもらう。
3. **受け入れ条件**: 次の書き方に従う。

**`acceptance.md` から写すとき**（手順2・3を省いたとき）は、次のようにする。
- 1 は、設計書の決定（Q-xx・R-xx・D-xx）を番号つきで表にする。
- 2 は、聞かずに置いた前提が無ければ「なし」と書く。
- 3 は、その実装単位の AC-N-x を全部、チェックボックスにして、**文言をそのまま**写す。下の「受け入れ条件の書き方」で整えない（形が違っても直さない）。
- 下の「抜けが無いか」の観点で足りないものに気づいても、条件を足さず、最後の報告に書く。設計書を先に直すかどうかは、人が決める。

#### 受け入れ条件の書き方

（質問して決めたときの書き方。`acceptance.md` から写すときは当てはめない。）

- 1 行 1 条件。形は「**〜すると、〜になる**」。チェックボックス（`- [ ]`）にする。
- **画面で見える結果**で書く。「テーブルに〜が入る」ではなく、「下書き一覧に表示される」「チャンネルのメッセージ一覧には出ない」のように、人が画面で確かめられる言い方にする。
- 数値と文言は具体的に書く（1,000文字ちょうどは保存できる・1,001文字はエラー、エラーの文言そのもの。値と文言は `screens.md` の4章）。上限は境界の両側を条件にする。
- 見出しでグループに分け、次の抜けが無いか確かめる。
  - 正常に動く（作る・見る・直す・消す）
  - 入力が不正なとき（空・長すぎ・境界）
  - 失敗したときの状態（エラーのあと、入力が残るか、データは増えないか）
  - 他人のもの・未ログイン・存在しない ID（403 / ログイン画面 / 404）
  - **今までの動きが変わらない**（チャンネルのメッセージ一覧・編集・削除、スレッドの返信、検索、既存テストが通る）
- 1 条件に動作を詰め込まない。「保存して、一覧に出て、チャンネルのメッセージ一覧には出ない」は、確かめる観点が違うなら分ける。

### 5. Issue にする

前提の確認が取れてから進める（前提が「なし」ならそのまま進む。本文の確認は 5-2 で必ず取る）。前提が直されたら、受け入れ条件を直してから Issue にする。
Issue は外に出る操作で、起票したあとに本文を直すと履歴が残る。だから、起票の前に必ず本文を見せて確認を取る。

#### 5-1. 本文を作る

次の見出しで書く。

| 見出し | 書くこと |
| --- | --- |
| 背景 | 今のアプリに何が無くて、なぜ要るのか。1〜2 文 |
| やること | 作るもの（テーブル・モデル・ルート・画面・Policy など）を箇条書きで。ルートは `POST /channels/{channel}/messages` のように URL まで書く。一覧で関連データを出すなら `with()`、認可は `ChannelPolicy`・`MessagePolicy` に揃える、など CLAUDE.md と設計書の決まりもここに入れる |
| 仕様 | 質問で決まったことと、「私が決めた前提」。上限・文言・権限・日時の扱い。`acceptance.md` から写したときは、設計書の決定とその番号（Q-xx・R-xx・D-xx） |
| 変えないこと | 今の動きのうち、触らないもの（チャンネルのメッセージ一覧・編集・削除、スレッドの返信、「編集済み」など）。今回やらないと決めたもの（`features.md` の2章にあるものは、そこから） |
| 完成の条件 | 手順 4 の受け入れ条件。チェックボックスのまま、**言い換えずにそのまま**入れる。設計書の受け入れ条件（AC-N-x）と食い違わせないため |
| テスト | 追加する Feature テストのファイル名（`tests/Feature/<機能>Test.php`）と、確かめる観点の箇条書き。`acceptance.md` の2章に TP-N-xx があれば、その番号で書く。`.claude/rules/testing.md` の決まりに合わせる |

タイトルは「〇〇機能を追加する」の形（例:「メッセージ検索機能を追加する」）。ラベルは `enhancement`。

#### 5-2. 見せて、確認を取る

本文を会話にそのまま出し、AskUserQuestion で聞く。選択肢の例:

- 「この内容で起票する」(Recommended)
- 「直してから起票する」（直す点を聞き、直した本文をもう一度見せる）
- 「起票しない」（会話に残すだけで終わる）

質問文には、タイトルとラベルも書く。人が見るのは質問ダイアログだけのことがあり、本文が画面から流れているかもしれないため。

#### 5-3. 起票する

承認を得たときだけ実行する。

1. 本文を、作業用の一時ディレクトリ（スクラッチパッド）に Markdown ファイルで書く。リポジトリには置かない。
2. `gh issue create --title "<タイトル>" --label enhancement --body-file <ファイル>` を実行する。本文を `--body` に直接渡さない。本文にはバッククォートや `$` が多く、シェルに解釈されて壊れるため。
3. 返ってきた Issue の URL と番号を報告する。

`gh` が使えない・認証が通っていないときは、起票できなかったと正直に伝え、本文のファイルの場所を示す。`gh auth login` はこちらで代わりに実行せず、`! gh auth login` を人に案内する。

### 6. 終わり方

- 起票した Issue の番号と URL、決まったこと、前提を、短くまとめて報告する。
- 最後に 1 行、次の一手を添える。たとえば「この Issue をもとに、`docs/design/` のどのファイルをどう直すかの案を出します」。設計書や実装に進むかどうかは、人が決める。
- 実装には進まない。設計書（`docs/design/`）も、書き始めの合図があるまで編集しない。

## 気をつけること

- 質問のために読むのであって、設計の答えを出すために読むのではない。読んで分かったことを「決定」にせず、人が決めることとして質問に変える。
- Issue を起票する権限は、「Issue にして」と言われたときや、このスキルを呼んだときの依頼から自動で生まれない。**起票のたびに、本文を見せたうえで確認を取る。**
- `.env`・`vendor/`・`node_modules/`・`storage/` は読まない（CLAUDE.md の決まり）。
- 受け入れ条件に出てくる文言は、CLAUDE.md の決まりにそって日本語にする。
