# Issue に着手する（ブランチを切る〜承認をもらって実装に入るまで）

Issue に着手するとき、手を動かす前の数手を飛ばすと、あとで効く。`main` に直接コミットしてしまう。設計書を読まずに作り手が黙って決める。設計書と食い違ったまま実装が進み、最後に設計書を直すはめになる。

このスキルは、そうならないように、コードを書く手前までを決まった順で進める。読み終えたあとは、件の大きさで2通りに分ける（手順5）。どちらも「承認」を取るまでコードは書かない。承認されたら実装に入る（実装そのものの進め方は、このスキルの範囲の外）。

## 入力

- **Issue の番号**: 依頼文から読む。無ければ聞く。

## 手順

### 1. Issue を読む

`gh issue view <番号>` で本文を読む。見るところは、「やること」「仕様」「変えないこと」「完成の条件」「テスト」。
「私が決めた前提」のように、起票した人が置いた前提があれば、違っていたら直す前提として覚えておく。Issue は実装単位（`docs/design/acceptance.md` の 1〜7）に当たる。

### 2. main を最新にして、ブランチを切る

1. `git status` で、未コミットの変更が無いか見る。あれば**触らずに**報告する（人が編集中のことがある）。
2. `git switch main` → `git pull origin main`。
3. pull が `Permission denied (publickey)` で失敗したら、そのことを報告したうえで、`gh` の認証で HTTPS から取得して同じ結果にする（この環境では SSH の鍵が通らないことがある）。

   ```bash
   gh auth status   # ログイン済みか
   git -c credential.helper= -c 'credential.helper=!gh auth git-credential' \
     fetch https://github.com/<owner>/<repo>.git +main:refs/remotes/origin/main
   git merge --ff-only origin/main
   ```

   `<owner>/<repo>` は `gh repo view --json nameWithOwner -q .nameWithOwner`。取得が「Already up to date」なのか、進んだのかを報告する（最新だと確かめられないまま進まない）。
4. ブランチ名は CLAUDE.md の「プルリクエスト」の表に従う。**Issue 1件は `feature/issue-<番号>-<英字の短い名前>`**（例: `feature/issue-1-auth`）。名前は Issue の題から付ける。**`main` には直接コミットしない**。

### 3. 読む

質問と計画は、このアプリの今の作りを読んでから考える。読まずに聞くと、どの機能にもある一般論しか出ない。

- `CLAUDE.md` の「実装前に必ず読む決定」と「決めごとの在りか」のうち、この Issue が触るところ。Issue 本文が指す設計書の章（`acceptance.md` の AC-N-x・TP-N-xx を含む）。**設計書の中身はここで覚えるだけで、計画には写さない**（計画では参照で指す。設計書が正本で、写すと2か所に決めごとができる）。
- 既存のコード: `app/`、`routes/web.php`、`database/migrations/`、`resources/views/`、`tests/Feature/`、`config/`。
- 食い違いの探し物: 設計書の形と既存の migration、設計書の決めと Issue の指示、Laravel が最初から用意している物のうち使わない物（`questions.md` の D-10）、設計書が「実装のときに決める」としている項目。

### 4. 決めないといけないことを質問する

設計書で決まっていることは聞かない。読んで「作り手が決めるしかない」と分かったものだけを、`AskUserQuestion` で聞く。**設計の選択はユーザーが決める**（CLAUDE.md）ので、推奨を先頭に置き、選択肢ごとに理由と代償を書いて、答えを待つ。

聞いたもの（例）: 既存テーブルの作り替え方（dbal が無く `->change()` が使えない）／既存の根拠の無いテーブルの扱い／CSS の置き場／共通の処理の置き場。

### 5. 件の大きさで分ける

読み終えたら、次の4つが**すべて**当てはまるかを見る。

- 触るファイルが少ない（目安は1〜3 ファイル）
- 設計書で決まっていて、手順4の質問が要らない
- 設計書や Issue との食い違いが無い（手順6に当たらない）
- migration・権限・公開APIの形・画面の状態（URL のクエリ）を変えない

すべて当てはまれば**小さい件**（5-B）。ひとつでも外れたら、ふつうの件（5-A）。迷ったら 5-A にする。計画を省いて黙って決めてしまうより、計画が少し重いほうが、あとで直す手間が小さいため。
この Issue は実装単位（機能1つ分）なので、たいてい 5-A になる。5-B は、文言の直し・設定の1行・テストの足しなど、作業が小さいときに使う。5-B で進めている途中で、質問が要ること・食い違いが見つかったら、5-A に切り替える。

#### 5-A. ふつうの件: プランモードで計画を立てる

プランモード（`EnterPlanMode`）に入り、計画ファイルに書く。計画ファイルはリポジトリには入れない（残すのは結果の設計書と PR）。

- **Context**: なぜこの変更か。参照する設計書の章（ファイルと ID）。
- **決めたこと**: 質問への回答。
- **実装**: 章ごと（データ／ルート／画面／テスト）。名前の付け方は Laravel の慣例。設計書の文言は写さず、「`screens.md` 4-2 の SC-02 の行のとおり」のように指す。
- **触らない**: Issue の「変えないこと」と、作らないもの。
- **確認（検証）**: 動かし方、テスト、受け入れ条件。ほかの単位に頼る行は、設計書の決め（`questions.md` の D-29）に従って「保留」にする。
- **PR の「確認してほしいこと」に書く点**: 自分で決めたこと。

#### 5-B. 小さい件: プランモードに入らず、何をするかだけ伝える

計画ファイルは作らない。次の4つを、短い文で伝える。

- 何をするか（直すファイルと、直す中身）
- 小さい件だと見た理由（上の4つに当てはまること）
- 確かめ方（走らせるテスト、見る画面）
- 触らないもの

そのあと**返事を待つ**。「着手してよいですか」と聞き、承認が来るまでコードは書かない。直してほしい点があれば、伝え直して、また待つ。

### 6. 設計書や Issue と食い違うとき

ユーザーの指示や実物が、設計書の決めと違うと分かったら、黙って実装しない。この場合は小さい件ではないので、必ず 5-A（プランモード）で進める。

1. どの決め（D-xx・章）と、どう違うかを示す。
2. **設計書を先に直す**（CLAUDE.md。実装と食い違ったら、コードではなく `docs/design/` を先に直す）。直す場所は `grep` で洗い出す（決めの本体、反映先の章、`.claude/skills/review-diff` の手順4、Issue 本文）。
3. 設計書は**「書き始めの合図」があるまで編集しない**。計画の先頭に「手順 0: 設計書の直し」として置き、承認と合図を待つ。
4. 設計書だけの変更も `main` に直接コミットしない。`chore/<英字の短い名前>` のブランチで PR にする（実装のブランチに混ぜるかは、聞く）。
5. 外に出る操作（`gh issue edit`、push）は、実行前に確認する。

### 7. 承認をもらって、実装に入る

- 5-A: `ExitPlanMode` で承認を求める。
- 5-B: 5-B で伝えた内容への返事を、承認とみなす。

承認されたら、実装に入る。最初に、`./vendor/bin/sail up -d`（mysql が healthy になるまで約30秒）で環境を起こす。保存のたびに動くフック（Pint・テスト）が、Sail が止まっていると失敗するため。実装の進め方（テスト・Pint・PR）は、CLAUDE.md と `.claude/rules/` に従う。承認の内容と違うことをしたくなったら、先に伝えて、もう一度承認をもらう。

## 報告の形

着手の最初の報告に、次を入れる。

- `main` の状態（最新だったか、どう取得したか）と、切ったブランチ名
- Issue の要点と、読んだ設計書
- 食い違いがあれば、その内容（なければ「なし」）
- 質問が必要なら、その質問

## やらないこと

- 承認をもらう前に、コードを書かない（5-A も 5-B も同じ）。
- `.env` を読まない・書かない。
- 未コミットの変更（人の編集）を、勝手に消したり、コミットに含めたりしない。
- push は頼まれたときだけ（CLAUDE.md）。
- 設計書の中身を、計画や報告に写さない。参照で指す。
