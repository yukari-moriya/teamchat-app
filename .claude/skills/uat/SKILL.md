# ブラウザで受け入れ条件を確かめる（UAT）

確かめる受け入れ条件は、次のとおりです。

$ARGUMENTS

受け入れ条件そのものではなく、それが書いてあるファイルの場所を渡されたときは、
そのファイルを開いて、書かれている受け入れ条件を読んでから始めてください。


## 入力

- **条件の行**: 依頼に書かれた行をそのまま使う。無ければ `docs/design/acceptance.md` の1章から、該当する実装単位の AC-N-x の行を使い、使う行を先に示す。
- **ログイン情報**: 依頼に書かれたもの。`.env` は読まない。足りなければ聞く。
- **URL**: 指定が無ければ `http://localhost`。
- **スクリーンショットの置き場**: 指定が無ければ `uat-shots/`（無ければ作る）。

## 準備

1. アプリが起きているか `curl -s -o /dev/null -w "%{http_code}\n" <URL>` で見る。起きていなければ `./vendor/bin/sail up -d`（CLAUDE.md の決まりどおり `./vendor/bin/sail` を頭に付ける）。
2. Playwright MCP の道具は最初は名前だけの遅延読み込み。`ToolSearch` で `playwright browser` を検索して読み込む。MCP がまだ接続中なら、検索が待ってくれる。
3. 設計書を読む（`docs/design/*.md`）。画面のつくり、期待するメッセージの文言、ルートを知っておくと、判定が速く正確になる。
4. スクリーンショットの置き場を作る。

## 手順

条件の行を**依頼の順に**1行ずつ確かめる。1行ごとに「操作 → 画面を読む → 撮る → 判定」を回す。

### 操作のコツ

- 要素の指定は、直前の `browser_snapshot` の `ref`、または `getByRole('button', { name: '…' })` の形で書く。`textbox "名前"` のような書き方は受け付けない。
- ページが遷移すると `ref` は変わる。遷移したら、次の操作の前に `browser_snapshot` を取り直す。
- 判定は、スクリーンショットだけでなく **snapshot の文字（メッセージ・件数・ボタンの有無）** で裏を取る。画像は人に見せる証拠、判定の根拠は文字。
- ユーザーを切り替えるときは、ログアウトしてから `/login` を開き直す。

### 前提のデータを探す

条件によっては、特定のデータが要る（例: 「返信が付いているメッセージ」）。**あると決めつけて撮らない。**
先に実在を確かめる。ログイン済みのブラウザで `browser_evaluate` から `fetch` で一覧を回し、該当するページを探すのが速い。
見つからなければ、その行は「前提のデータが無い」と報告するか、条件を満たす操作（投稿など）を先にやってから確かめる。どちらにしたかを報告に書く。

### データを変える操作

- 触るのは、今回の確認で自分が作ったデータか、「UAT 用」と分かるデータだけにする。既存の他のデータは消さない・書き換えない。
- 作ったデータは、確認が終わるまでに消して元に戻す。条件が「消せること」なら、その確認で元に戻る。
- 戻したら、確認前と同じ状態かを報告に書く（件数など）。

### 認可（「他人のものは操作できない」）の確かめ方

画面にボタンが出ていないだけでは、サーバーが拒否している証拠にならない。次の2つを両方やる。

1. **画面**: 他人としてログインして、ボタンが出ていないことを撮る。
2. **サーバー**: 同じセッションで `browser_evaluate` から直接リクエストを送り、ステータスを見る。CSRF トークンはページ内の `meta[name=csrf-token]` か `input[name=_token]` から取り、`POST` に `_method=DELETE` を付けて送る。期待するステータスは `docs/design/permissions-api.md` の1-5に従う（見られないチャンネル＝存在しない・メンバーでないプライベートは 404、見られるチャンネルでの権限の無い操作は 403）。
   - 対象の ID は、`./vendor/bin/sail artisan tinker --execute='…'` で読んで調べる（読み取りだけ。`.env` は読まない）。
   - 送ったあと、画面を開き直し、tinker でも、データが残っていることを確かめる。

## スクリーンショット

- 保存は `browser_take_screenshot` の `filename` に `uat-shots/…` を指定する。`fullPage: true` で撮る。
- **ファイル名は行番号から始め、中身が分かる名前にする。** 例: `01-thread-with-replies.png`、`03-empty-body-error.png`。1行で複数枚なら `04a-…`、`04b-…` と枝を付ける。
- **撮る前に、その画面が名前どおりの中身かを snapshot で確かめる。** 名前と中身が合わない画像を残さない。合わないものを撮ってしまったら、消して撮り直す（`rm`）。
- 画面が同じ状態になる2枚が、同じ画像になることはある。その場合は報告に一言書く。

## 報告

### 表の形

1行1条件で、次の列にする。

| # | 確認すること | 判定 | 判断の理由 | 証拠 |
|---|---|---|---|---|

- **判定**は `満たす` / `満たさない` / `判定できない` のどれか。
- **判断の理由**には、画面で見た**具体的な事実**を書く。メッセージの文言、件数の変化（例: 3件から4件）、ステータスコードなど。「問題なく動いた」だけは書かない。
- **証拠**にはスクリーンショットのパスを書く。1行に複数あるときは、何を示す画像かを添える。
- `満たさない` のときは、何をしたら何が起きたか（期待と実際）を書く。原因の推測は、確かめていなければ推測と書く。
- `判定できない` のときは、足りない物（前提のデータ、ログイン情報など）を具体的に書く。推測で `満たす` にしない。

### 表のあとに

- 確認でデータを変えたなら、何を作り何を消したか、最後の状態が確認前と同じかを書く。
- 途中で想定と違ったこと（前提のデータを探し直した、撮り直した、など）は、短く書く。
- `uat-shots/` と `.playwright-mcp/` は git で追跡されていない。コミットするかは人が決めるので、**勝手に `git add` / コミットしない**。追跡されていないことだけ伝える。

## やらないこと

- アプリのコード・設計書・テストを直さない。
- `.env` を読まない・書かない。値が要るときは聞く。
- 他のユーザーのデータを、確認のためだと言って消さない。
- テスト（`sail test`）の代わりにしない。この手順は画面から見た確認で、自動テストの結果は別に報告する。
